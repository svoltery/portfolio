# Техническое задание на интеграцию

**Kafka | Корневой сервис уведомлений | Продюсер**

| Параметр | Значение |
|---|---|
| Версия | 1.0 |
| Статус | Черновик |
| Сервис-продюсер | `notification-service` |
| Сервис-консюмер | APNs-адаптер |
| Основной топик | `notification-ios` |
| DLQ-топик | `notification-ios-dlq` |
| Тип интеграции | Асинхронная, Apache Kafka |

## 1. Цель задачи

Реализовать публикацию сообщений о Push-уведомлениях из корневого сервиса уведомлений в топик Kafka `notification-ios` для последующей обработки APNs-адаптером.

Обеспечить сохранение порядка уведомлений одного пользователя, повторную публикацию при временных ошибках и передачу сообщений, которые не удалось опубликовать, в DLQ.

### 1.1. Контекст

Корневой сервис уведомлений отвечает за подготовку уведомлений к отправке: определение получателя, канала доставки, текста и приоритета.

Для отправки Push-уведомлений на устройства iOS используется APNs-адаптер, который получает сообщения из Kafka и взаимодействует с Apple Push Notification service по HTTP/2.

Подготовленные уведомления сохраняются в таблице `outbox`. Для каждого активного iOS-устройства создаётся отдельная запись. Публикацию записей в Kafka выполняет отдельный воркер корневого сервиса.

### 1.2. Ожидаемый результат

- Корневой сервис публикует сообщения в топик `notification-ios`.
- Для каждого активного iOS-устройства пользователя создаётся отдельная запись `outbox`.
- Сообщения одного пользователя направляются в одну партицию Kafka.
- Публикация уведомлений одного пользователя выполняется в порядке их создания.
- Ошибки публикации обрабатываются с помощью повторных попыток и DLQ.
- Состояние публикации каждой записи фиксируется в БД.

## 2. Границы задачи

### В scope

- Формирование Kafka-сообщений для APNs-адаптера.
- Контракт сообщения: `key`, `headers`, `value`.
- Настройка топиков `notification-ios` и `notification-ios-dlq`.
- Настройка Kafka Producer.
- Реализация отдельного воркера для публикации из `outbox`.
- Публикация отдельного Kafka-сообщения для каждой записи `outbox`.
- Обеспечение порядка публикации уведомлений одного пользователя.
- Обновление состояния публикации в БД.
- Повторные попытки и обработка ошибок.

### Вне scope

- Реализация Kafka Consumer в APNs-адаптере.
- Отправка HTTP-запросов в APNs.
- Обработка ответов APNs.
- Вызов gRPC `ReportPushFailure`.
- Переключение с Push на SMS.
- Sequence Diagram — оформляется отдельным файлом PlantUML.

## 3. Настройка топиков

### 3.1. Основной топик

| Параметр | Значение |
|---|---|
| Название топика | `notification-ios` |
| Партиции | Определяет разработчик |
| Replication Factor | 3 (предлагается) |
| `retention.ms` | `604800000` (7 дней, предлагается) |
| `max.message.bytes` | `1048576` (1 МБ, предлагается) |
| Формат сообщения | JSON, UTF-8 |

### 3.2. DLQ-топик

| Параметр | Значение |
|---|---|
| Название топика | `notification-ios-dlq` |
| Назначение | Хранение сообщений, публикация которых завершилась ошибкой после допустимых повторных попыток либо невозможна из-за некорректных данных |
| Формат | Исходное сообщение и дополнительные заголовки с информацией об ошибке |
| Партиции, репликация, retention | Определяются разработчиком |

При полной недоступности Kafka публикация в DLQ также может быть невозможна. В таком случае сообщение должно оставаться в БД до восстановления возможности публикации.

## 4. Контракт данных

Сообщение Kafka состоит из ключа (`key`), заголовков (`headers`) и тела (`value`).

### 4.1. Структура сообщения

| Часть | Поле | Тип | Обяз. | Описание | Источник данных |
|---|---|---|---|---|---|
| KEY | `key` | string | Да | Идентификатор пользователя для определения партиции | `outbox.user_id` |
| HEADER | `idempotency-key` | string | Да | Уникальный идентификатор сообщения | `outbox.id` |
| HEADER | `trace-id` | string | Да | Идентификатор для трассировки | `outbox.id` |
| VALUE | `device_token` | string | Да | Push-токен устройства iOS | `user_device.push_token` |
| VALUE | `title` | string | Да | Заголовок Push-уведомления | `notification_template_text.title` |
| VALUE | `message` | string | Да | Подготовленный текст уведомления | `outbox.message` |
| VALUE | `priority` | integer | Да | Бизнес-приоритет уведомления | `category.priority` |
| VALUE | `category` | string | Да | Категория уведомления | `category.category` |
| VALUE | `created_at` | datetime ISO 8601 | Да | Время создания уведомления в UTC | `outbox.created_dt` |

### 4.2. Правила формирования

1. Для каждого активного устройства пользователя с `platform = ios` и `is_active = true` создаётся отдельная запись в `outbox`.
2. На основании каждой записи `outbox` со статусом `new` формируется отдельное Kafka-сообщение.
3. В качестве Kafka Key каждого сообщения используется `outbox.user_id`.
4. Поле `message` передаётся в готовом виде, после подстановки значений переменных шаблона.

### 4.3. Пример сообщения

**Kafka Key**

```text
u001
```

**Kafka Headers**

```text
idempotency-key: 15
trace-id: 15
```

**Value**

```json
{
  "device_token": "example-ios-device-token",
  "title": "Подтверждение операции",
  "message": "Подтвердите операцию в приложении.",
  "priority": 1,
  "category": "сервисное",
  "created_at": "2026-10-19T12:30:00Z"
}
```

## 5. Логика продюсера

### 5.1. Условия публикации

Сообщение публикуется в `notification-ios`, если:

1. Уведомление подготовлено к отправке по каналу Push на устройство iOS.
2. В таблице `outbox` существует соответствующая запись со статусом `new`.
3. Для записи доступен непустой Push-токен устройства.

### 5.2. Публикация через Outbox

Публикацию сообщений выполняет отдельный воркер корневого сервиса.

1. Корневой сервис сохраняет подготовленное уведомление в `outbox` со статусом `new`. Для каждого устройства создаётся отдельная запись.
2. После успешного коммита транзакции записи становятся доступны воркеру.
3. Воркер выбирает записи со статусом `new` в порядке `created_dt ASC, id ASC`.
4. Для каждой выбранной записи `outbox` формирует Kafka-сообщение согласно контракту раздела 4.
5. Воркер публикует сообщение в топик `notification-ios`.
6. После получения подтверждения от Kafka обновляет соответствующую запись `outbox`:
   - `status = published`;
   - `published_dt` — дата и время успешной публикации;
   - `kafka_message_id` — идентификатор опубликованного сообщения по принятому в системе правилу.

Если публикация завершилась ошибкой, запись остаётся доступной для повторной обработки.

### 5.3. Формирование ключа Kafka

```text
key = outbox.user_id
```

Пример: `u001`.

Продюсер передаёт строковый идентификатор пользователя. Kafka-клиент вычисляет хэш ключа и определяет партицию.

При неизменном количестве партиций и алгоритме партиционирования сообщения с одинаковым `user_id` направляются в одну партицию.

Это необходимо для сохранения порядка уведомлений одного пользователя.

### 5.4. Порядок публикации

Воркер должен публиковать уведомления одного пользователя в порядке их создания:

```sql
ORDER BY outbox.created_dt ASC, outbox.id ASC
```

Следующее уведомление пользователя не должно опережать предыдущее из-за повторных попыток публикации.

Порядок между уведомлениями разных пользователей не гарантируется.

### 5.5. Формирование idempotency-key

Для каждого Kafka-сообщения используется идентификатор соответствующей записи `outbox`:

```text
idempotency-key = String(outbox.id)
```

Пример: `15`.

При повторной публикации той же записи `outbox` значение `idempotency-key` не изменяется.

### 5.6. Настройки продюсера

| Параметр | Значение | Назначение |
|---|---|---|
| `acks` | `all` | Подтверждение записи всеми синхронизированными репликами партиции (ISR) |
| `enable.idempotence` | `true` | Предотвращение дублирования сообщений при повторных попытках Kafka Producer |
| `retries` | Настраиваемое значение | Повторные попытки при временных ошибках Kafka |
| `delivery.timeout.ms` | Определяет разработчик | Максимальное время ожидания результата публикации |

Для `enable.idempotence = true` должны соблюдаться совместимые настройки Kafka Producer, в том числе `acks = all`, `retries > 0` и `max.in.flight.requests.per.connection <= 5`.

## 6. Обработка ошибок продюсера

| Ситуация | Действия системы |
|---|---|
| Kafka подтвердила публикацию | Обновить статус соответствующей записи `outbox` на `published` |
| Kafka временно недоступна | Выполнить повторную попытку публикации |
| Истёк тайм-аут подтверждения | Зафиксировать ошибку; повторить публикацию с тем же `idempotency-key` |
| Ошибка сериализации или некорректные данные | Не отправлять сообщение в основной топик; передать в DLQ при доступности Kafka |
| Ошибка конфигурации топика или авторизации | Зафиксировать ошибку в логах и мониторинге; передать на устранение |
| Исчерпаны повторные попытки | Передать сообщение в DLQ, если Kafka доступна; иначе сохранить для последующей обработки |

### 6.1. Сообщения DLQ

В DLQ передаётся исходное сообщение с дополнительными заголовками:

| Header | Тип | Описание |
|---|---|---|
| `error-reason` | string | Причина ошибки публикации |
| `error-timestamp` | datetime ISO 8601 | Время фиксации ошибки |
| `retry-count` | integer | Количество выполненных повторных попыток |
| `original-topic` | string | `notification-ios` |

Публикация в DLQ не должна приводить к потере исходной записи `outbox`.

### 6.2. Дополнительные условия

- При повторной публикации сохраняются Kafka Key, `idempotency-key` и `trace-id`.
- Повторная публикация не должна нарушать порядок уведомлений одного пользователя.
- После исчерпания повторных попыток ошибка фиксируется в логах и мониторинге.
- Количество попыток, интервалы и тайм-ауты определяются конфигурацией интеграции.
- Повторная обработка записи `outbox` может привести к появлению дубликатов в Kafka; заголовок `idempotency-key` позволяет консюмеру их идентифицировать при наличии соответствующей логики.

## 7. Нефункциональные требования

| Параметр | Требование |
|---|---|
| Семантика доставки | At-least-once на уровне публикации из Outbox; возможны повторные сообщения |
| Порядок сообщений | Для одного пользователя сохраняется порядок публикации уведомлений |
| Маршрутизация | Сообщения одного пользователя направляются в одну партицию |
| Отказоустойчивость | Временная недоступность Kafka не приводит к удалению необработанных записей |
| Повторная публикация | Сохраняются Kafka Key, `idempotency-key` и `trace-id` |
| Логирование | Фиксируются идентификатор записи `outbox`, топик и результат публикации |
| Мониторинг | Контроль ошибок, повторных попыток, DLQ и необработанных записей `outbox` |
| Максимальный размер сообщения | В пределах ограничений топика |

## 8. Открытые вопросы

1. **Связь записи с устройством.** Как фиксируется устройство, для которого создана запись `outbox`? Предлагается добавить `user_device_id` с внешним ключом на `user_device.id`.
2. **`kafka_message_id`.** Какой идентификатор публикации сохраняется в этом поле? Kafka предоставляет метаданные записи (топик, партицию, offset), но не создаёт отдельный универсальный message ID.
3. **Повторные попытки.** Сколько попыток выполняется и какие интервалы используются?
4. **DLQ.** Как организуется повторная обработка сообщений из DLQ после устранения ошибки?
5. **Количество партиций.** Какое значение используется и допускается ли его изменение после запуска интеграции?
