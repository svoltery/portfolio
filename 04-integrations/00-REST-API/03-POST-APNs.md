# 1. Исходящие интеграции

## 1.1. Интеграция с APNs

**Метод и URL:** POST /3/device/{device_token}

**Назначение:** эндпоинт для отправки push-уведомлений на устройства с ОС IOS

**Инициатор:** сервис-адаптер APNs

**Условие для отправки запроса:** получено событие из топика notification-ios

**Headers:** все описанные заголовки обязательны для отправки

| Header | Значение | Описание |
| --- | --- | --- |
| :method | POST | Обязательный заголовок в APNs |
| :path | /3/device/{device_token} | Обязательный заголовок в APNs, где {device_token} - токен устройства нашего пользователя |
| host | api.push.apple.com:443 | prod для отправки уведомлений |
|  | api.sandbox.push.apple.com | dev для отправки уведомлений |
| authorization | bearer JWT | Для авторизации запроса |
| apns-push-type | alert | Тип уведомлений - обычное уведомление |
| apns-topic | ru.zanachka.bank | Bundle ID нашего приложения в экосистеме Apple |
| apns-id | traceId | TraceId наших запросов в системе, берем из сообщения в Kafka |
| apns-priority | 10 или 5 | Приоритет доставки: 10 - уведомления с priority:1 ; 5 - все остальные уведомления |

### Тело запроса (пример):

```json
{
  "aps": {
    "alert": {
      "title": "Новое сообщение",
      "body": "У вас новое сообщение"
       },
   }
}
```

### Заголовки ответа:

| Header | Значение | Описание |
| --- | --- | --- |
| apns-id | traceId | TraceId наших запросов в системе |
| :status | 200/400/403/404/405/413/429/500/503 | HTTP статус-код о состоянии ответа |
| apns-unique-id | ny56h4-tnrs3-gefe-4dfbr-dher4 | Идентификатор уведомления, доступный для среды разработки, по нему можно отследить логи уведомления в Push Notifications Console |

### Тело ответа (успех): 
При успешной отправке push-уведомления тело ответа возвращается пустым

### Тело ответа (ошибка):

```json
{
  "reason": "BadDeviceToken"
}
```

### Что делаем при ошибке / недоступности:

| Header | Значение | Response-body | Описание | Что делаем |
| --- | --- | --- | --- | --- |
| :status | 400 | { "reason": "BadDeviceToken" }<br> | Неверный токен пользователя | Вызываем gRPC метод *название*, перезаписываем токен пользователя в запросе, retry с новым токеном. Если токен не обновился - шлем сообщение об ошибке в топик notification-responce и логируем WARN |
| :status | 400 | все остальные варианты reason | Некорректный запрос к APNs. Конкретная причина определяется значением reason. | Не выполнять автоматический retry; сохранить WARN с reason в логах/мониторинге. |
| :status | 403 | { "reason": "BadCertificate" }<br>ИЛИ<br>{ "reason": "ExpiredProviderToken" }<br>ИЛИ<br>{ "reason": "InvalidProviderToken" } | Ошибка аутентификации запроса к APNs. | Не повторять тот же запрос. Логируем ERROR. Проверить/обновить данные интеграции. |
| :status | 404 | { "reason": "BadPath" } | Указанный в запросе endpoint не соответствует допустимому endpoint APNs | Не повторять. Исправить формирование endpoint. |
| :status | 405 | { "reason": "MethodNotAllowed" } | Указанное значение в заголовке не равно :method:POST | Ошибка контракта, необходимо исправить интеграцию в кодовой базе |
| :status | 410 | { "reason": "ExpiredToken" }<br>ИЛИ<br>{ "reason": "Unregistered" } | APNs сообщает, что токен пользователя больше не действителен. | Вызываем gRPC метод *название*, перезаписываем токен пользователя в запросе, retry с новым токеном. Если токен не обновился - шлем сообщение об ошибке в топик notification-responce и логируем ERROR |
| :status | 413 | { "reason": "PayloadTooLarge" } | Размер сообщения (тела запроса) слишком большой | Не делаем retry, шлем сообщение об ошибке в топик notification-responce и логируем ERROR |
| :status | 429 | { "reason": "TooManyRequests" } | APNs ограничил частоту запросов. | Выждать время для retry, отправить сообщение заново. Если после N retry сообщение не доставлено - отправляем сообщение в топик notification-responce и логируем ERROR |
| :status | 500 | { "reason": "InternalServerError" } | Ошибка со стороны сервера APNs | Для некритичных уведомлений (“priority”: 2) - повторить отправку с retry/backoff policy, при неуспехе - шлем сообщение об ошибке в топик notification-responce и логируем ERROR. Для критичных уведомлений (“priority”: 1) сразу шлем сообщение об ошибке в топик notification-responce и логируем ERROR.<br> |
| :status | 503 | { "reason": "ServiceUnavailable" }<br>ИЛИ<br>{ "reason": "Shutdown" } | Ошибка со стороны сервера APNs | Для некритичных уведомлений (“priority”: 2) - повторить отправку с retry/backoff policy, при неуспехе - шлем сообщение об ошибке в топик notification-responce и логируем ERROR. Для критичных уведомлений (“priority”: 1) сразу шлем сообщение об ошибке в топик notification-responce и логируем ERROR.<br> |

### Последовательность отправки сообщения:

1. Вычитываем сообщение из топика notification-ios;
2. Формируем POST-запрос к серверу APNs;
3. Отправляем POST-запрос:
   - При успехе (получили 200 от APNs) - отправляем сообщение в топик notification-response со статусом success
   - При неудаче (получили код ошибки от APNs) отправляем сообщение в топик notification-response со статусом warn/error (см. пункт Что делаем при ошибке / недоступности)
