# gRPC: ReportPushFailure

## 1. Контекст

Метод `ReportPushFailure` нужен, чтобы APNs- и FCM-адаптеры сообщали корневому сервису о неуспешной отправке критичного Push-уведомления с `priority = 1` (категория «сервисное/безопасность»).

Адаптер передаёт идентификатор уведомления и причину ошибки. Дальнейший переход на SMS выполняет корневой сервис.

## 2. Триггер вызова

Адаптер вызывает `ReportPushFailure`, если отправка Push-уведомления с `priority = 1` завершилась одной из указанных ниже ошибок.

### APNs

| HTTP-код | Причина ошибки (`reason`) | Условие вызова |
|---|---|---|
| `400` | `BadDeviceToken` | После проверки обновлённого токена, если отправка не удалась |
| `410` | `ExpiredToken`, `Unregistered` | После проверки обновлённого токена, если отправка не удалась |
| `413` | `PayloadTooLarge` | Сразу после ошибки |
| `500` | `InternalServerError` | Сразу после ошибки, без повторной отправки Push |
| `503` | `ServiceUnavailable`, `Shutdown` | Сразу после ошибки, без повторной отправки Push |

### FCM

| HTTP-код | Код ошибки | Условие вызова |
|---|---|---|
| `400` | `INVALID_ARGUMENT` | Если ошибка связана с недействительным токеном устройства |
| `404` | `UNREGISTERED` | Сразу после ошибки |
| `500` | `INTERNAL` | Сразу после ошибки, без повторной отправки Push |
| `503` | `UNAVAILABLE` | Сразу после ошибки, без повторной отправки Push |

### Общие правила

- `priority = 1` — критичное уведомление; при перечисленных ошибках адаптер вызывает `ReportPushFailure`.
- Для уведомлений с другим приоритетом метод не вызывается. Адаптер применяет свою политику повторных попыток и передаёт итоговый результат через Kafka.
- Ошибка `429 Too Many Requests` не запускает немедленный вызов gRPC: адаптер выполняет повторные попытки с задержкой.

## 3. Описание метода

| Параметр | Значение |
|---|---|
| Сервис | `NotificationService` |
| Метод | `ReportPushFailure` |
| Назначение | Передать корневому сервису сведения о неуспешной отправке критичного Push-уведомления и причину ошибки |
| Инициатор | APNs-адаптер или FCM-адаптер |
| Получатель | Корневой сервис уведомлений |
| Тип взаимодействия | Unary: один запрос — один ответ |
| Протокол | gRPC |

### Параметры запроса

| Поле | Тип | Обязательность | Описание |
|---|---|---|---|
| `notification_id` | `int64` | Да | Идентификатор уведомления (`outbox.id`) |
| `failure_reason` | `string` | Да | Причина неуспешной отправки, полученная от Push-провайдера |

### Параметры ответа

| Поле | Тип | Описание |
|---|---|---|
| `accepted` | `bool` | Подтверждает, что корневой сервис принял сообщение о неуспешной отправке к обработке |

`accepted = true` не означает, что SMS уже отправлено или доставлено.

## 4. Proto-контракт

```proto
syntax = "proto3";

package notification.v1;

service NotificationService {
  rpc ReportPushFailure(ReportPushFailureRequest)
      returns (ReportPushFailureResponse);
}

message ReportPushFailureRequest {
  int64 notification_id = 1;
  string failure_reason = 2;
}

message ReportPushFailureResponse {
  bool accepted = 1;
}
```

## 5. Коды ответов

| gRPC-код | Условие | Результат |
|---|---|---|
| `OK` | Сообщение о неуспешной отправке принято | `accepted = true` |
| `INVALID_ARGUMENT` | Не передан `notification_id`, он некорректен или пустой `failure_reason` | Запрос отклонён |
| `NOT_FOUND` | Уведомление с указанным `notification_id` не найдено | Запрос отклонён |
| `FAILED_PRECONDITION` | Уведомление не соответствует условиям вызова метода (не является критичным либо для него не предусмотрен fallback на SMS) | Запрос отклонён |
| `UNAVAILABLE` | Корневой сервис временно недоступен | Вызов можно повторить |
| `DEADLINE_EXCEEDED` | Истекло время ожидания ответа | Результат вызова неизвестен; возможен повтор |
| `INTERNAL` | Непредвиденная ошибка корневого сервиса | Вызов завершён с ошибкой |

## 6. Повторные попытки (retry)

- При `UNAVAILABLE` и `DEADLINE_EXCEEDED` адаптер повторяет вызов с теми же `notification_id` и `failure_reason`, используя задержку между попытками с увеличением интервала (exponential backoff).
- При `INVALID_ARGUMENT`, `NOT_FOUND` и `FAILED_PRECONDITION` автоматические повторные вызовы не выполняются.
- При `INTERNAL` автоматический повтор не выполняется до определения причины ошибки.
- Максимальное количество попыток, интервалы между ними и тайм-аут вызова определяются конфигурацией интеграции.
- Корневой сервис должен обеспечивать идемпотентную обработку повторных вызовов для одного уведомления, чтобы повторный запрос не приводил к повторному запуску fallback.
- После исчерпания повторных попыток адаптер фиксирует ошибку в логах и мониторинге.

## 7. Границы метода

Метод передаёт сведения о неуспешной отправке Push и возвращает подтверждение их принятия. Запись результата в `delivery_attempt`, проверка условий резервной отправки, формирование SMS и публикация события в Kafka выполняются корневым сервисом и не входят в описание данного gRPC-контракта.
