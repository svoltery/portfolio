### 1.3. Vision & Scope

**Контекст и проблема:**

Внутри банковской системы существует сервис путешествий, на который пользователь может оформить ежемесячную подписку. На данный момент отсутствуют какие-либо уведомления о сроке действия/завершении этой подписки. Пользователь может не воспользоваться преимуществами подписки на Travel-сервис или прекратить её использование. Необходимы уведомления о жизненном цикле подписки.

**Бизнес-цель:**

- G1 - Увеличить долю пользователей, продлевающих подписку на сервис путешествий после окончания текущего периода подписки, на 10% относительно показателя до внедрения уведомлений.
- G2 - Снизить количество обращений пользователей в службу поддержки, связанных с неожиданным автопродлением подписки на сервис путешествий, на 20% относительно показателя до внедрения уведомлений.

### 1.5. Границы задачи

**В задачу входит:**

1. Обработка событий жизненного цикла подписки Travel.
2. Одна категори уведомлений - сервисные.
3. Отправка уведомлений через Push (FCM для Android, APNs для iOS) с фолбэк на SMS (SMSC.ru, HTTP/REST).
4. Приоритеты доставки, частотный лимит, учёт согласия пользователя на обработку персональных данных.
5. Формирование текста уведомления.
6. Логирование результата отправки.

**В задачу не входит:**

1. Иные средства доставки информации о подписке:
   - E-mail - нет интеграции и согласий, отдельный бэклог.
   - Мессенджеры (Telegram, WhatsApp) - отдельный бэклог.
   - Голосовые звонки - не канал уведомлений.
2. Остальные категории уведомлений - информационные и маркетинговые:
   - Уведомления о билетах и отелях - задача посвящена жизненному циклу подписки, а не Travel-транзакциям
3. Оформление, отмена и продление подписки — выполняются в Travel-сервисе; система уведомлений только информирует пользователя.
4. Изменение тарифов - управление тарифами является ответственностью Travel-сервиса.

### 1.7. Бизнес-правила

| ID | Правило | Источник |
| --- | --- | --- |
| BR-1 | Уведомления о состоянии подписки Travel относятся к сервисным уведомлениям и не требуют отдельного согласия пользователя на рекламную рассылку. | Комплаенс |
| BR-2 | Повторное событие с тем же идентификатором не порождает второе уведомление (дедупликация) | Архитектура |
| BR-3 | Сервисные уведомления о состоянии подписки не должны отправляться в установленный период ночного ограничения. | Бизнес / комплаенс |
| BR-4 | Для сервисных уведомлений о подписке используются Push и SMS; при недоставке Push применяется резервный канал SMS. | PO / существующие правила системы уведомлений. |
| BR-5 | В системе должно быть действующее согласие пользователя об обработке ПД. | Комплаенс |

### 1.8. Допущения

1. У клиента актуальный push-токен устройства; иначе основной канал - СМС.
2. SMSC.ru доступен с заявленным SLA; при недоступности уведомление остается в очереди.
3. Согласия клиента хранятся в профиле и доступны системе.
4. Таймзона клиента известна для расчета тихих часов.
5. Travel-сервис является источником истины по состоянию подписки и передаёт в Kafka события об изменении её состояния.

### 1.9. Ограничения

1. 152-ФЗ (персональные данные).
2. Лимиты провайдеров: длина СМС, rate limits FCM/APNs.
3. Срок релиза – конец 4 квартала.
4. Сценарии уведомлений ограничены следующими событиями жизненного цикла подписки: оформление, изменение тарифа, приближение окончания.
5. Типы подписки - базовая, семейная.
