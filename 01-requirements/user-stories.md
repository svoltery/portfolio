# User Storie

Шаблон заполнен сквозной историей US-1 — напоминание о дате платежа. История выбрана, потому что напрямую закрывает бизнес-цель G1: снизить долю клиентов, пропустивших дату платежа по кредитной карте, с 18% до 12%.

## 1. User Story с критериями приемки

**ID:** US-1

**Название:** Напоминание о дате платежа по кредитной карте

### Формулировка

Как клиент с кредитной картой,
я хочу заранее получать напоминание о дате и сумме платежа,
чтобы не допустить просрочку и не платить штраф.

**Приоритет:** Must

**Связь:** Бизнес-цель G1 (снизить пропуски платежа с 18% до 12%); бизнес-правила BR-3, BR-4; функциональные требования FR-6, FR-7; Use Case UC-1.

**Категория уведомления:** Сервисное критичное — отправляется по договору, согласие на рекламу и тихие часы не применяются (BR-3).

### Критерии приемки (Given–When–Then)

#### AC-1. Успешный путь: push доставлен

* **Дано:** у клиента подключены push-уведомления, есть валидный токен устройства, до даты платежа остается 3 дня.
* **Когда:** система обрабатывает событие о приближении даты платежа из Kafka.
* **Тогда:** клиенту отправляется push с датой платежа и суммой, СМС не отправляется, статус — «доставлено».

#### AC-2. Отказ: push не доставлен, фолбэк на СМС

* **Дано:** событие обработано, push отправлен, но подтверждение доставки не получено.
* **Когда:** истек порог ожидания 30 секунд.
* **Тогда:** напоминание отправляется по СМС через SMSC.ru, статус — «фолбэк» (FR-6, BR-4).

#### AC-3. Отказ: токен устройства невалиден

* **Дано:** FCM или APNs вернул ошибку невалидного токена.
* **Когда:** система пытается отправить push.
* **Тогда:** токен помечается невалидным, напоминание сразу уходит по СМС без ожидания порога, инициируется обновление токена (процесс — TBD, у мобильной команды).

#### AC-4. Отказ: СМС-шлюз недоступен

* **Дано:** нужен фолбэк на СМС, SMSC.ru не отвечает.
* **Когда:** система пытается отправить СМС.
* **Тогда:** событие остается в очереди, выполняется ретрай, поднимается алерт; при исчерпании ретраев статус — «ошибка» и эскалация.

#### AC-5. Краевой случай: дубль события

* **Дано:** Kafka доставила одно и то же событие дважды.
* **Когда:** система обрабатывает второе событие с тем же ключом дедупликации.
* **Тогда:** повторное уведомление не отправляется, факт дубля фиксируется в логе.

#### AC-6. Краевой случай: нет ни push, ни телефона

* **Дано:** у клиента нет валидного токена устройства и нет подтвержденного номера телефона.
* **Когда:** система пытается доставить напоминание.
* **Тогда:** статус — «недоставлено» с указанием причины, событие эскалируется для разбора.

#### AC-7. Правило: тихие часы не блокируют сервисное уведомление

* **Дано:** время отправки попадает в тихие часы 22:00–09:00 по таймзоне клиента.
* **Когда:** обрабатывается напоминание о платеже (категория «критичное»).
* **Тогда:** уведомление отправляется без задержки, правило тихих часов не применяется (BR-3).
